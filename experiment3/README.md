## 四、实验原理

1. **列表 list**：动态数组，存储的是对象引用。切片会生成新序列，而 `del 列表[切片]` 是**原地批量删除**：Python 先按删除前的原列表一次性算出所有目标下标，再统一删除。因此遍历过程中删除元素极易产生漏删。
2. **元组 tuple**：不可变指的是元组内部存储的**引用地址**不可修改，并不限制引用所指向的可变对象被修改。只要元组内任意一个元素不可哈希，整个元组就不可哈希。
3. **集合 set**：基于哈希表实现，支持 `&`、`|`、`-`、`^` 四种运算。普通 `set` 可变、不可哈希，不能嵌套；固定集合用 `frozenset`（可哈希，可以放进集合）。
4. **哈希判定**：只有生命周期内 `hash` 值固定不变的对象才是可哈希对象。数值、字符串、元素均可哈希的元组、`frozenset` 可哈希；`list`、`dict`、`set`、`bytearray` 不可哈希。
5. **去重**：`list(set(ls))` 简洁但丢失原有顺序，且要求元素可哈希；保序去重可利用「新列表 + 已见集合」或 `dict.fromkeys()`（Python 3.7 起字典保持插入顺序）。

## 八、预判与结果对比分析（任务1 重点）

### 8.1 三组切片删除

| 代码 | 原列表 | 命中索引（按删除前） | 手写预判 | 实际运行 | 是否一致 |
| --- | --- | --- | --- | --- | --- |
| `del ls1[::3]` | `[0..9]` | 0, 3, 6, 9 | `[1,2,4,5,7,8]` | `[1,2,4,5,7,8]` | 一致 |
| `del ls2[1::3]` | `[0..9]` | 1, 4, 7 | `[0,2,3,5,6,8,9]` | `[0,2,3,5,6,8,9]` | 一致 |
| `del ls3[::-2]` | `[0..5]` | 5, 3, 1 | `[0,2,4]` | `[0,2,4]` | 一致 |

**原因分析**：三组预判与实测完全一致，关键在于 `del 列表[切片]` **按删除前的原索引一次性计算**，不是「删一个就重新编号」的动态索引。`slice.indices(n)` 会先把切片规约成 `(start, stop, step)`，例如 `[::-2]` 在长度 6 上得到索引 `5, 3, 1`，Python 再一次性删掉这三个位置。因此负步长只是「从末尾往前取下标」，删除后剩下的元素仍按原相对顺序排列。

如果误以为是动态索引，就会算错：例如 `del ls[::3]` 若删掉索引 0 后重新编号，下一个「每 3 个」会落到原索引 4 而不是 3，结果会完全不同。实测 `[1,2,4,5,7,8]` 证明删除始终以原列表为基准。

### 8.2 循环删除的 bug（重点）

指导书给出的 `[1,2,3,4,5,6]` 用 `for i in ls4: if i % 2 == 0: ls4.remove(i)` 得到 `[1,3,5]`，**看起来删干净了，但这只是数据恰好没触发问题**。换成含连续偶数的数据即可暴露缺陷：

```text
[1, 2, 2, 4, 6, 3]  →  [1, 2, 6, 3]     ← 偶数 2 和 6 被漏删
```

**原因**：`for` 循环内部维护一个递增下标，每轮 +1；一旦删除元素，后面的元素整体前移一位，于是**下一个元素被跳过检查**；同时 `remove(x)` 按值只删除第一个匹配项。上例中删掉第一个 `2` 后，第二个 `2` 前移到当前下标，但循环下标已经前进，它就永远不会被判定；删掉 `4` 后 `6` 前移，同样被跳过。

**安全修改方案**（源码中三种均已实现，结果均为 `[1,3]`）：

```python
# ① 列表推导式（推荐，生成新列表，不动原列表）
[x for x in risky if x % 2 != 0]

# ② 倒序按下标删除（原地，前移的只是已处理过的元素，不影响后续下标）
for i in range(len(ls) - 1, -1, -1):
    if ls[i] % 2 == 0:
        del ls[i]

# ③ 遍历快照，操作原列表
for x in ls[:]:
    if x % 2 == 0:
        ls.remove(x)
```

### 8.3 任务2 逐条辨析

| 表达式 | 结果 | 理由 |
| --- | --- | --- |
| `(1, 2, 3)` | 成功 | 元素全是 int，均可哈希，元组整体可哈希 |
| `(1, [2, 3])` | `TypeError: unhashable type: 'list'` | 含 list，整体不可哈希 |
| `[1, 2]` | `TypeError: unhashable type: 'list'` | list 可变，本身不可哈希 |
| `frozenset({1, 2})` | 成功 | 不可变集合，创建后内容固定，hash 稳定 |
| `{1, 2}` | `TypeError: unhashable type: 'set'` | 普通 set 可变，不可哈希 |

补充验证：`t = (1, [2, 3])` 后执行 `t[1].append(4)` 得到 `(1, [2, 3, 4])`，说明元组的「不可变」只约束引用地址，不约束引用对象的内容；但 `t` 依旧不能放进集合。

**`frozenset` 的作用**：它是不可变、可哈希的集合，因此可以作字典键或另一个集合的元素。当业务需要「集合里存放集合」时，内层必须使用 `frozenset`。

### 8.4 任务4 两种去重方案优缺点

| 方案 | 结果 | 优点 | 缺点 |
| --- | --- | --- | --- |
| `list(set(data))` | `[1,2,3,5,7,9]` | 一行、O(n) | **丢失原始顺序**；要求元素可哈希；顺序不稳定 |
| 手写「新列表 + `not in`」 | `[5,2,7,9,3,1]` | 完全保序、逻辑直观 | `not in 列表` 是线性查找，O(n²)，数据量大时慢 |
| 「新列表 + `seen` 集合」 | `[5,2,7,9,3,1]` | 保序且 O(n) | 需要额外一个集合，元素必须可哈希 |
| `list(dict.fromkeys(data))` | `[5,2,7,9,3,1]` | 一行、保序、O(n) | 依赖 Python 3.7+ 字典保序；元素必须可哈希 |

**易错点**：本例 `list(set(data))` 输出 `[1,2,3,5,7,9]` 恰好是升序，容易被误认为「有序」。这只是巧合——CPython 中小整数的 `hash` 值等于自身，哈希桶恰好按顺序排列。换成字符串 `["banana","apple","cherry",...]` 立刻得到与原始顺序不一致的结果，足以证明 `set` 无序。

### 8.5 任务5 每一步输出的文字解释

- **①** 先去重再统计，`class1` 中重复的 `103`、`101` 和 `class2` 中重复的 `102` 只算一次；保序去重保证编号按首次出现顺序排列：`[101,103,105,107,109]` 与 `[102,104,106,108,109,107]`。
- **②** `s1 & s2 = [107, 109]`：同时出现在两个班的编号，即交集。
- **③** `s1 ^ s2 = [101,102,103,104,105,106,108]`：只出现在其中一个班的编号，等价于 `(s1|s2) - (s1&s2)`，注意它不包含交集中的 107、109。
- **④** `s1 - s2 = [101,103,105]`：以 1 班为基准做差，只保留不在 2 班的编号；与 ③ 的区别在于它只关心「1 班独有」这一侧。
- **⑤** `(107, 109)`：交集元素是 `int`，不可变且可哈希，元组可以容纳，也能直接放进集合或作字典键；若元素是 `list` 这类不可哈希对象则不行。
- **拓展**：`nest = [[1,2],[3,4],[1,2],[5,6]]` 的内层 `list` 不可哈希，先 `tuple(inner)` 转成可哈希键去重，再保留或转回列表，结果 `[[1,2],[3,4],[5,6]]`。

## 九、思考题（必答）

**1. `del ls[::3]` 是按删除前索引计算还是动态实时索引？举例说明。**

按**删除前的原索引一次性计算**，不是动态实时索引。以 `ls = [0,1,...,9]` 为例，`[::3]` 规约出下标 `0,3,6,9`，Python 一次性删掉这 4 个位置，结果 `[1,2,4,5,7,8]`。若按动态索引，删掉索引 0 后列表变为 `[1,2,3,...]`，下一个「每 3 个」会落在原索引 4，结果必然不同。负步长 `[::-2]` 同理：先算出 `5,3,1` 再统一删除。

**2. `t = (1,[2,3])`，为什么 `t[1].append(4)` 合法，但 `t` 不能放入集合？**

元组的「不可变」指内部保存的**引用地址**不能改，`t[1]` 始终指向同一个 list 对象，向该 list 追加元素只是修改对象内容，并没有改动元组里的引用，所以合法，结果 `(1,[2,3,4])`。但可哈希要求对象生命周期内 `hash` 值固定，元组只要含有一个不可哈希元素（此处是 list）就整体不可哈希；`set` 基于哈希表，插入前必须计算 `hash`，因此 `s.add(t)` 抛 `TypeError: unhashable type: 'list'`。

**3. 为什么普通 `set` 不能嵌套，`frozenset` 可以作为集合元素？**

普通 `set` 可变（可 `add`/`remove`），内容一变 `hash` 就会变，所以不可哈希，不能作为另一个集合的元素，字面量 `{ {1,2} }` 也会直接报 `TypeError`。`frozenset` 创建后内容固定，因此可哈希，既能作集合元素也能作字典键，是实现「集合嵌套集合」的标准做法。

**4. 使用 `for` 遍历列表同时 `remove` 元素为什么删不干净？给出一种安全的修改方案。**

`for` 用递增的内部下标推进，删除元素后后续元素整体前移，导致下一个元素被跳过；且 `remove(x)` 按值只删第一个匹配项，重复值更容易残留。最安全的方案是**不原地改，用列表推导式生成新列表**：

```python
ls = [x for x in ls if x % 2 != 0]
```

若必须原地修改，可倒序按下标 `del`，或遍历快照 `for x in ls[:]`。

**5. `list(set(数据))` 去重的缺陷是什么？保序去重有哪些实现方式？**

缺陷有两点：① `set` 无序，去重后**丢失原始顺序**（本例升序只是小整数哈希的巧合）；② 要求元素可哈希，遇到嵌套 list / dict 会 `TypeError`。保序去重实现方式：

1. 新列表 + `if x not in out: out.append(x)`（直观，O(n²)）；
2. 新列表 + `seen` 集合记录已出现元素（O(n) 且保序）；
3. `list(dict.fromkeys(data))`（一行，依赖 Python 3.7+ 字典保序，最推荐）；
4. 老版本可用 `collections.OrderedDict.fromkeys(data)`。

## 十、实验小结

### 三种容器对比

| 容器 | 有序 | 可变性 | 元素约束 | 典型适用场景 |
| --- | --- | --- | --- | --- |
| `list` | 有序 | 可变 | 无 | 需要保持顺序、频繁增删改、按下标访问 |
| `tuple` | 有序 | 引用不可变 | 无（但整体可哈希要求元素均可哈希） | 固定记录、函数多返回值、作字典键 / 集合元素 |
| `set` | 无序 | 可变 | 元素必须可哈希 | 去重、快速成员判断、交并差等集合运算 |

### 哈希约束总结

可哈希 = 生命周期内 `hash` 值固定且可判等。可哈希：数值、字符串、元素均可哈希的 `tuple`、`frozenset`；不可哈希：`list`、`dict`、`set`、`bytearray`。哈希约束直接决定了「能不能放进集合 / 作字典键」，也是本次实验任务2、任务5 拓展题的核心考点。

### 收获

- 切片删除必须按「删除前的原索引」理解，切勿与循环中的动态索引混淆；
- 「元组不可变」要区分引用不可变与对象内容可变，这是最容易混淆的概念；
- 任何「边遍历边修改」的写法都应警惕，优先用推导式或快照；
- 去重不只是「去掉重复」，还要明确是否需要保序、元素是否可哈希，据此在 `set` / `seen` 集合 / `dict.fromkeys` 之间选择；
- 集合运算中，交集、差集、对称差语义不同（对称差不含交集元素），综合统计时应先去重再运算，并对每一步输出配文字解释。
